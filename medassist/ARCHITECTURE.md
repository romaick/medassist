# МедАссистент 0.8.2: архитектура

Локальное HTML/CSS/JavaScript-приложение открывается в окне установленного Edge или Chrome. Сервер, установка библиотек и подключение к МИС не требуются. Рабочие функции не обращаются к внешней сети.

Поликлинический интерфейс, поиск и новые черновики используют history.complaints. Старое поле reason сохраняется для совместимости данных, но не показывается и не включается при генерации. Повод обращения планируется для будущего стационарного режима; этот режим ещё не реализован. Ручные черновики сохраняются дословно.

В0.7.1 меню показывает обзор, пациентов, нового пациента, текущий приём (если выбран), повторные приёмы, модули, помощь и данные, проверку обновлений. Верхняя панель использует18px для даты и20px для времени; формат и частота обновления прежние.

Верхняя панель показывает местные дату и время компьютера: «12 ноября(11) 2000», ЧЧ:ММ. Название месяца берётся из Intl.DateTimeFormat ru-RU с днём для родительного падежа. Один таймер обновляет только два элемента time, не перерисовывая форму и не изменяя записи. После возврата во вкладку время обновляется сразу.

## Слои

Исправления 0.5.1 после полного демонстрационного приёма: дата в заголовке и счётчики анамнеза/показателей обновляются при вводе; после генерации фокус переходит к редактору. Явный repository.load() повторно читает хранилище даже после прежней ошибки, снимая блокировку записи только после успешного разбора актуальных данных. Это позволяет загрузить резервную копию, восстановленную другим окном. save() самостоятельно блокировку не снимает. Формат данных и правила формирования текста не изменены.

## ФИО и постоянные UI-проверки

«ФИО пациента» — пользовательское название patient.label, до120 символов. Поле доступно на первом шаге приёма и в карточке, его HTML формируется одним helper. При вводе в приёме пациент определяется по active().patientId, независимо от ранее открытой карточки. Меняются label/updatedAt пациента и заголовок; даты и ручные тексты приёмов не переписываются. В версии 0.7 изменение имени также возвращает проверенные записи этой карточки в статус draft и очищает reviewedAt. Записи других пациентов не затрагиваются.

Постоянный tests/ui-patient.test.cjs запускается через node --test с существующим Playwright (MEDASSIST_PLAYWRIGHT) и установленным Edge. Два окна одного нового тестового контекста проверяют конфликт, отсутствие лишнего приёма, закрытие диалога, видимость toast через elementFromPoint и успешное продолжение после явной загрузки. Отдельный сценарий проверяет ФИО двух пациентов, общую карточку/приёмы, сохранность черновиков и длинное имя на разных ширинах. Запуск входит в обязательные проверки, инструкции — в README. Зависимости не добавлены.

tests/ui-workflow.test.cjs проверяет список повторных дат, явные отметки и статусы записи, повторное открытие связанной записи без дубликата, возврат в черновики при изменениях и конфликты окон. Используется отдельный контекст браузера с вымышленными данными; пользовательский профиль не открывается. Результаты конкретного выпуска фиксируются в CHECKS.txt.

## Список пациентов в0.7.2

renderPatientList использует существующую проекцию core.getReturnVisits. Для каждой карточки выбирается первая незавершённая дата>=сегодня и первая прошедшая незакрытая дата. Предстоящая дата задаёт приоритет0, только прошедшая —1, отсутствие назначений —2. Сортировка: приоритет, дата↑, patient.updatedAt↓, patient.id↑. Отметки completed исключены. Последний приём по прежнему определяется visitDate/createdAt/id в истории; он не подменяется датой явки. Прошедшая незакрытая дата показана отдельно даже при наличии будущей. Поиск по имени/коду сохраняет порядок. Изменения календарного дня обновляют только список, не поле поиска и не данные. Новый постоянный UI-сценарий проверяет эти правила, смену отметки состоявшегося приёма, отсутствие записей в хранилище при просмотре и разные ширины. Схема и формат сохранения прежние.

## Карточки и модель версии 4

Резервная копия: {format: "medassist-demo", schemaVersion: 4, exportedAt, patients, encounters}. Карточка patient содержит id, label (условное имя до120 символов), createdAt, updatedAt. Приём сохраняет поля v3, обязательный patientId и получает workflow. Идентификаторы карточек и приёмов независимы; каждый приём должен ссылаться на существующую карточку. До500 карточек и500 приёмов. Карточки без приёмов допустимы. Неизвестные/пропущенные поля, неверные типы, повторные ID и отсутствующие ссылки отклоняются до записи.

Карточка показывает историю по visitDate убывающе, затем createdAt и id; изменение старого черновика не делает его самым поздним посещением. Новый пациент создаётся вместе с первым приёмом. Условное имя меняется в карточке и видно в связанных приёмах. Пол и возраст принадлежат конкретному приёму.

createRepeatEncounter(source,{carryHistoryFields}) создаёт приём с новым id и прежним patientId. Только явно перечисленные conditions/medications/allergies копируются дословно. Возраст, пол, остальные поля анамнеза, осмотр, показатели, заключение, больничный, дата повторного приёма и черновик пустые; workflow получает начальные значения. Источник функция не изменяет. Диалог позволяет выбрать исходный приём того же пациента, увидеть содержимое трёх полей и отметить каждое отдельно. Изначально отметок нет; смена источника их снимает. Кнопка «Создать приём» подтверждает выбор. Отмена не создаёт запись. При конфликте окон создание останавливается. При запуске из плана повторов источник закреплён за выбранной датой, а создание дополнительно сохраняет связь плана с новой записью.

Клинические разделы приёма:
- history: жалобы, начало, течение, заболевания/операции, постоянные препараты, аллергии, дополнительный анамнез.
- examSelections: отдельные значения из каталога. Ритм и звучность тонов независимы; новые поля пусты.
- exam: уточнения и исходные описания0.1; не превращаются в признаки автоматически.
- vitals: измерения без клинической интерпретации; ИМТ вычисляется из массы и роста.
- assessment: диагноз, рекомендации, старый свободный followUp, дата повторного приёма, отметка/номер/период больничного.
- draft: редактируемый текст, дата генерации, отпечаток исходных полей. Карточка не перезаписывает ручной текст. patientId не входит в отпечаток: появление карточки само по себе не делает старый черновик устаревшим.

Пустые дополнительный анамнез, другие данные осмотра, рекомендации и повторный приём не создают строк. Больничный отражается только при yes; номер перед датами. Повторный приём завершает черновик. Программа не оформляет нормативные документы.

## План повторных приёмов и проверка записи

workflow содержит reviewStatus: 'draft' | 'reviewed', reviewedAt: ISO-строка | '', returnVisitStatus: 'planned' | 'completed', returnVisitEncounterId: ID | ''. У новой записи, нового повтора и при миграции прежних записей начальные значения — draft, пустая reviewedAt, planned и пустая ссылка. Статус записи и факт состоявшегося приёма независимы.

getReturnVisits(encounters,todayYYYYMMDD) выбирает записи с assessment.returnVisitDate и возвращает encounterId, patientId, date, bucket и linkedEncounterId. Раздел «Повторные приёмы» группирует их по местной дате компьютера: today — «Сегодня», upcoming — «Ближайшие» (все будущие даты без ограничения горизонта), past — «Дата прошла», completed — «Состоявшиеся» независимо от даты. Порядок внутри группы: дата по возрастанию, затем ID. Прошедшая дата сама по себе не означает неявку или состоявшийся приём.

setReturnVisitStatus(entry,status) изменяет только отметку плана. «Отметить: состоялся» и «Вернуть в план» требуют явного подтверждения; клинический текст и статус проверки врача не меняются. completed допускается только при назначенной дате. Из списка можно открыть карточку или начать повтор. Если returnVisitEncounterId уже заполнен, кнопка открывает эту запись; повторно она не создаётся. Создание новой записи не ставит отметку «Состоялся» автоматически.

linkReturnVisit(source,target) связывает план только с другой записью того же пациента. Одна цель принадлежит одному плану; ссылки на себя, отсутствующую запись, другого пациента и циклы отклоняются при проверке всего набора. Без назначенной даты допустимы только planned и пустая ссылка. Изменение или удаление даты сбрасывает отметку и связь; ранее созданная запись остаётся в истории пациента.

setReviewStatus(entry,status,{now}) возвращает запись с новым статусом. «Отметить: проверено врачом» доступно как явное действие на вкладке «Запись»: текст должен быть непустым, поля должны проходить техническую валидацию, а врач подтверждает проверку текста и его соответствия форме. Это личная отметка, не электронная подпись и не автоматическая оценка медицинского содержания. reviewed получает время проверки; возврат в draft очищает его. На главной доступны фильтры «Все», «Черновики» и «Проверено врачом»; незавершённые записи — все записи draft.

Изменение клинических полей, текста черновика, повторная генерация и применение нормального осмотра возвращают затронутую запись в draft. Изменение ФИО снимает проверку всех связанных записей пациента. Метаданные workflow не входят в fingerprint генератора: отметки проверки и состоявшегося приёма сами по себе не делают текст устаревшим.

Перед созданием, завершением и проверкой записи, в том числе после модального подтверждения, проверяется отсутствие конфликта с другим окном. Связанный повтор и изменения плана сохраняются одним bundle. Ошибка сохранения откатывает изменение состояния интерфейса; конфликт требует явной загрузки актуальных данных.

## Совместимость и хранение

parseBundle принимает версии 1/2/3/4. Каждый приём из v1/v2 получает отдельную карточку с id=encounter.id, пустым label и прежними createdAt/updatedAt; encounter.patientId равен тому же id. Карточки и связи из v3 сохраняются. Все записи прежних версий получают начальный workflow со статусом draft. Результат детерминирован; автоматического объединения похожих пациентов нет. Все исходные строки и ручные черновики сохраняются. Для v1 дополнительно вводятся пустые поля v2. Новую резервную копию со статусами и связями повторов открывает версия 0.7 и новее.

Хранилище читает medassist.demo.v4, при отсутствии — v3, затем v2 и v1. Чтение и миграция не записывают данные. save(encounters,patients) и reset(encounters,patients) проверяют обе коллекции и сохраняют их одной записью только в v4. Ключи v1/v2/v3 остаются нетронутыми. Повреждённое приоритетное сохранение блокирует обычную запись и не подменяется устаревшей копией. Явная успешная повторная загрузка снимает блокировку. События изменения любого из четырёх ключей останавливают автосохранение в другом окне.

## Ограничения и расширение

Для file: URL поведение localStorage зависит от браузера. Перед обновлением, перемещением папки, сменой профиля или очисткой браузера нужен JSON-экспорт. Очистка списка 0.7 заменяет карточки и приёмы в v4 пустыми массивами; старые ключи v1/v2/v3 и файлы на диске не удаляются.

Только вымышленные данные. Нет шифрования, авторизации, аудита, клинических рекомендаций, МИС и нормативных форм Беларуси. Соответствие медицинской эксплуатации не оценивалось. Каталог осмотра — инструмент записи, а не полный стандарт обследования.

Будущим модулям нужны отдельные контракты, версии, проверки и источники. Официальным документам — проверка применимости, редакции и даты.

## Независимое интернет-обновление

Отдельный Update-MedAssist.cmd запускает Windows PowerShell 5.1 и окно обновления. update-channel.json содержит HTTPS-адрес опубликованного пакета. Адрес канала: https://raw.githubusercontent.com/romaick/medassist/main/release/medassist-update.json. Пользователь явно разрешил создание публичного репозитория и загрузку программы. Pin-MedAssist.cmd создаёт два ярлыка на рабочем столе, не заменяя ярлыки, ведущие в другую папку. Политики выполнения PowerShell не меняются.

Пакет medassist-update формата 1 содержит версию x.y.z, dataSchemaVersion=4 для выпуска 0.7 и ровно девять разрешённых файлов app. Каждый файл представлен Base64 и SHA-256; version.json должен совпадать с пакетом. HTTPS удостоверяет сервер при стандартной проверке сертификата; хеши выявляют повреждение и несогласованность, но не заменяют цифровую подпись издателя. Доверие к каналу обновления означает доверие опубликованному коду.

Пакет не содержит приёмы, настройки браузера, секреты, тестовые профили или файлы проекта sources. Скрипт обновления не читает хранилище браузера и не отправляет данные приёмов. Запрещены HTTP, перенаправления, произвольные пути и лишние файлы. Проверка и подготовка выполняются до замены; старая папка сохраняется, журнал позволяет восстановить прерванную замену. Два обновления одновременно блокируются. Путь app/index.html не меняется; фактическая сохранность данных проверяется в том же профиле Edge.

Пакет обновляет только app и не доставляет оболочку. Для перехода установленной версии 0.6 на 0.7 требуется однократно сохранить резервную копию и заменить updater/Update-Core.ps1 совместимой версией из репозитория. Она принимает только целые схемы 2/3/4 и проверяет совпадение схемы и версии пакета с вложенным version.json. Прежний обновлятор 0.6 отклоняет схему 4; для ещё более ранних версий замена также необходима. В новой установке из актуального архива совместимый файл уже включён. Проверка файлов, HTTPS, журнал, резервирование и откат не изменены. Другие файлы настроенной оболочки 0.6 заменять не требуется. Во время замены окна приложения и обновления должны быть закрыты. После публикации следующего совместимого проверенного выпуска пользователь получает его без участия чата.

Источники технических решений: [GitHub REST contents](https://docs.github.com/en/rest/repos/contents) — размещение файла и адрес raw; [Microsoft HttpClientHandler.AllowAutoRedirect](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclienthandler.allowautoredirect?view=netframework-4.8.1) — управление перенаправлениями. Цифровая подпись издателя не реализована. Результат проверки сетевого канала фиксируется отдельно. Результаты локальных проверок — CHECKS.txt.

## Поликлинический режим и версия 0.4.0

Пользователь определил два будущих режима: поликлинический и стационарный. Текущие формы и генератор относятся к поликлиническому режиму, что явно показано в интерфейсе. Стационарный режим не реализован. Его набор документов, жизненный цикл госпитализации и разделение данных будут определены отдельным контрактом до реализации; фиктивный переключатель и неизвестные клинические правила не добавляются.

Кнопка у каждого раздела осмотра выбирает нормальные значения только его полей из существующего каталога. Подтверждение зависит только от отклонений внутри выбранного раздела. Уточнения, измерения, другие разделы и ручной черновик сохраняются; общая кнопка остаётся доступна.

calculateBmi(weightKg, heightCm) вычисляет массу / (рост / 100)² и возвращает строку с одним десятичным знаком и запятой. Значение показывается рядом с массой/ростом и включается в новый черновик после роста. Оно выводится из исходных измерений, отдельного поля в JSON нет: при добавлении ИМТ в выпуске 0.4 сохранялась схема 2, текущая схема — 4. Пустые, некорректные, неположительные и нечисловые результаты не отображаются, как и крайние значения, округляющиеся до нуля или требующие экспоненциальной записи. Автоматическая клиническая классификация не выполняется.

Дата повторного приёма — последнее поле раздела «Запись» и последняя строка нового черновика, после больничного и старого свободного наблюдения. Пустая дата не выводится. Сохранённые ручные черновики не меняются без повторной генерации.

## Кнопка обновления, версия 0.5.0

Start-MedAssist.cmd вызывает updater/Register-UpdateLink.ps1, который регистрирует отдельную URI-схему для каждой установки в HKCU/Software/Classes. Имя medassist-update-<32 hex> содержит первые 32 символа SHA-256 от полного пути установки, приведённого к нижнему регистру .NET и без завершающего разделителя. Это идентификатор папки, не пароль и не подтверждение личности вызывающей страницы. Чужая регистрация с тем же именем не заменяется.

Обработчик запускает только фиксированный абсолютный путь Windows PowerShell с -File Update-MedAssist.ps1 этой установки. Подстановки %1 нет: URI, параметры, команды и записи приёмов не передаются. Любая страница может попытаться открыть схему; это способ запустить проверку, а установка остаётся отдельным подтверждаемым действием в штатном обновляторе. Политики PowerShell, настройки браузерных разрешений и привилегии пользователя не меняются.

Готовая схема передаётся из запускающего файла в фрагмент #updates=<схема>. JS принимает только file: URL и точный шаблон имени из 32 строчных hex-символов. Это устраняет разницу Unicode-нормализации JavaScript и .NET. Фрагмент сохраняет прежний путь app/index.html; фактическая сохранность localStorage проверена отдельно. Кнопка «К содержимому» переводит фокус без изменения фрагмента. При прямом открытии HTML или старой оболочке показывается инструкция. Приложение сообщает только о запросе запуска; результат проверки выводит нативное окно, поскольку обратного канала в браузер нет.

Новые файлы запуска нужно доставить один раз отдельно от девяти app-файлов. Исторически в выпуске 0.5 сохранялись формат обновления 1 и схема данных 2; текущая схема описана выше. Уже настроенные установки продолжают получать app-пакеты после установки совместимого Update-Core.ps1; старой установке 0.3/0.4 без новой оболочки доступен прежний отдельный обновлятор. Команды DescribeOnly и LaunchToken позволяют проверить контракт; тесты выполняют настоящую активацию Windows с обычными и неожиданными URI в изолированных временных папках.

Проверенные источники: [Microsoft: Registering an Application to a URI Scheme](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa767914(v=vs.85)) — ключ URL Protocol, команда запуска и риски передаваемых параметров; [Microsoft: Handle URI activation](https://learn.microsoft.com/en-us/windows/apps/develop/launch/handle-uri-activation) — недоверенные URI и отсутствие идентификации вызывающего приложения. Старое описание реестра использовано вместе с фактическими проверками текущей Windows; оно само по себе не доказывает поведение Edge. Результаты и непроверенные ограничения — CHECKS.txt.


## Рубрики и фильтры пациентов (0.8.0)

В 0.8.0 раздел «Пациенты» содержит рубрики «Все пациенты», «На больничном», «Повторная явка» и «Незавершённые записи». Рубрики пересекаются; счётчики показывают число пациентов до фильтрации. Поиск работает по ФИО, коду пациента и номеру выданного ЛН. Фильтры явки, последнего приёма и статуса записи можно сочетать. Сортировка — по явке, окончанию действующего ЛН, последнему приёму или ФИО. «Сбросить фильтры» очищает условия внутри выбранной рубрики.

В рубрике «На больничном» показаны пациенты с действующим по введённым датам ЛН либо неполным периодом. Отдельные условия: действует по датам, заканчивается сегодня, за ближайшие 3 дня (сегодня и следующие 2), период не указан полностью. Неполный период помечен как требующий уточнения и не считается действующим. Программа отражает сведения из приёмов и не подтверждает открытие или закрытие документа. Прошедшие и ещё не начавшиеся полные периоды доступны через «Все пациенты» и поиск номера.

Фильтры — временное состояние интерфейса, не часть сохранения. Schema4, ядро, хранилище и обновлятор не менялись. patientRows строит проекцию по всей истории; getReturnVisits исключает completed. Повторная явка включает прошлые незавершённые даты, «Не назначена / все состоялись» означает отсутствие незавершённых назначений. Диапазон дат проверяется на одной явке; последняя дата приёма берётся независимо. 7 дней — сегодня и следующие6, все границы включительны. Пустой диапазон явки включает любое незавершённое назначение; обратный диапазон даёт видимую ошибку и пустой список. Есть черновики — хотя бы один draft; все проверены — непустая история без draft. Для ЛН учитывается только sickLeaveIssued=yes; номер HTML-экранируется, одинаковые номер/начало/конец отображаются один раз. Текущие ЛН сортируются по окончанию, неполные периоды без подтверждённой текущей даты — в конце. Без фильтра явки сохраняется прежний порядок предстоящих, прошлых и отсутствующих назначений. Общие фильтры переживают переходы между рубриками, условия ЛН и сортировка сбрасываются к умолчаниям рубрики. Изменение календарного дня обновляет результаты и счётчики, не записывая данные. Постоянные UI-сценарии проверяют пересечения, границы, несколько записей, пропуски, поиск, сортировку, сброс, отсутствие записи в localStorage и смену суток.


## Поиск и скрытые фильтры (0.8.1)

В 0.8.1 фильтры в разделе «Пациенты» изначально скрыты. Нажмите «Фильтры», чтобы показать условия явки, статуса записей, сортировки и дат. При сворачивании выбранные условия продолжают действовать и видны над списком. «Сбросить фильтры и поиск» очищает их внутри текущей рубрики.

Поиск работает по всей истории: ФИО, код пациента или приёма, дата приёма, повторная явка, номер выданного больничного, текст анамнеза/осмотра/диагноза/рекомендаций и ручной записи. Выберите «Все параметры» либо конкретное поле в «Искать по». Даты можно вводить как 19.10.2026, 2026-10-19 или 19 октября 2026. Несколько слов применяются совместно к одному приёму с ФИО/кодом пациента. Поиск включает состоявшиеся явки; фильтры явки, как прежде, учитывают незавершённые назначения. Под совпавшим пациентом доступны кнопки открытия найденных приёмов.

patientSearchScope и patientFiltersOpen — состояние памяти окна, без изменения schema4/localStorage. Сброс возвращает режим поиска all, но сохраняет рубрику и раскрытие панели. Кнопка имеет aria-expanded/aria-controls, доступна с клавиатуры. Сводка условий, сброс и ошибка диапазона находятся вне скрываемой панели. Поиск нечувствителен к регистру, ё/е и повторным пробелам; полные русские даты и даты с названием месяца приводятся к ISO. Числовая часть даты и название месяца также доступны для частичного поиска. Все слова должны встретиться в данных одного приёма с идентичностью его пациента, совпадения из разных приёмов не объединяются. Ищутся только пользовательские поля, без workflow, sourceFingerprint, timestamp сохранения и других служебных полей. Текст осмотра включает выбранные фразы каталога; генератор черновика для поиска не запускается. В режиме номера ЛН учитывается только sickLeaveIssued=yes. Результаты не дублируют карточки, найденные записи доступны по их id; список более3 совпавших приёмов свёрнут в details. Постоянный UI-сценарий проверяет поля поиска, исторические/состоявшиеся даты, совместные слова, старый приём, сворачивание/сброс/ошибки диапазона/клавиатуру/ширины и отсутствие записи в хранилище.


## Единый поиск с ранжированием (0.8.2)

В 0.8.2 в разделе «Пациенты» оставлена одна строка поиска без выбора параметра. Введите фамилию, жалобу, диагноз, дату, номер больничного или несколько ключевых слов. Поиск охватывает всю историю. Сначала показаны результаты с большим числом совпавших слов, затем учитываются точность совпадения и поле: ФИО и коды имеют преимущество при равном качестве. Точное слово выше его части, часть слова выше небольшой опечатки. У результата видны причина совпадения и фрагмент подходящей записи; найденный приём можно сразу открыть.

Распознаются регистр, ё/е, несколько форматов даты и одна опечатка в словах от 5 букв. Номера и даты приблизительно не подбираются. Для нескольких ключевых слов допускается совпадение не менее двух третей слов с явной пометкой; все части запроса, содержащие цифры, обязательны. Слова из разных приёмов не складываются в полное совпадение. Рубрика и фильтры ограничивают результаты. Пока введён запрос, основной порядок — по совпадению; при очистке строки возвращается выбранная сортировка. Панель фильтров по-прежнему изначально скрыта.

patientSearchScope удалён; schema4, core/storage/updater без изменений. Запрос нормализуется один раз, слова дедуплицируются. Для каждого пациента оцениваются идентичность и каждый отдельный приём вместе с ней. Используется максимум, без суммирования по повторным упоминаниям или нескольким приёмам. Ранг: число найденных слов, сумма качеств (целое слово3, подстрока2, одна правка1), веса полей (ФИО/код пациента6, код приёма/номер ЛН5, даты/жалобы/диагноз4, анамнез/осмотр/рекомендации2, ручной текст1). При равенстве действует выбранная сортировка. Отдельные найденные приёмы тоже упорядочены по совпадению, затем по дате. Правка: вставка/удаление/замена/перестановка соседних букв, только буквенные слова запроса длиной>=5. Для кодов/номеров/дат fuzzy выключен. Неполное совпадение допускает ceil(2N/3) уникальных слов с обязательными числовыми частями. Пустой запрос показывает обычный список, запрос только из пунктуации даёт пустой результат. Причина и ограниченный фрагмент текста экранируются. Подбор не выполняет семантический анализ диагнозов или синонимов.
